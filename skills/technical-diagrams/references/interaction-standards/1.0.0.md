# 单向交互与架构排版规范 1.0.0

稳定 ID：`single-direction`。本规范约束交互方向、返回表达、系统边界、对齐、跨线和逻辑编号；与图种、视觉 profile、独立 `line_style` 分开版本化。编号和配色不因加载本规范而改变，直角 / 圆角 / 曲线仍按本次线条选择执行。

## 1. 一根有向线只表示一个方向

消息、调用、流转和依赖的每条有向路径只在终点放一个方向箭头。不把请求与返回压成一条双头线；若需表达返回，增加独立的反向虚线，并使用分离的端口和通道。

请求或处理调用使用实线，已有业务模型中的返回、受理与完成确认使用虚线。箭头方向、线型与标签须一致；不能只改线型而保留错误端点。检查实际生效的 SVG 箭头，包括父级 CSS 继承，不能只搜索路径自身的 `marker-start` 属性。

复绘旧的双向调用时，将模型中的两种交互拆成两个有向关系，分别记录参与方、事件、角色及编号。若旧图没有给出返回含义，不凭空编造协议码、结果或新业务分支；按来源保留可确认部分并明确不确定点。

## 2. 方向向上，不等于同步返回

Webhook、业务结果提交、异步回调虽然沿反向通道回传内容，仍可属于一个独立请求，须画实线并注明“独立请求”。对应 HTTP／处理确认另画反向虚线。

必须区分：

| 交互角色 | 线型 | 编号示例 |
| --- | --- | --- |
| 发起业务请求 | 单向实线 | 02 |
| 受理确认 | 独立单向虚线 | 02-R |
| 处理完成后发起的业务回调 | 单向实线，注明独立请求 | 05b |
| 回调接收方处理完成确认 | 独立单向虚线 | 06 |
| 只读结果查询与查询响应 | 实线查询、虚线响应分别绘制 | 07 / 08，或 16-Q / 16-R |

按具体来源区分“收到 / 受理”“业务成功”“事务已提交”，不让受理应答代替业务结果。涉及可靠接收和事务确认时，确认箭头不得提前到持久化成功之前。响应时间与异常码来自本次协议资料，不复制示例或过去项目的值。

## 3. 先定边界，再统一网格

系统归属按组织、部署与真实职责证据判断。调用关系不表示包含关系：外部平台对接的下游机构、银行或第三方服务，应放在独立系统边界中；不能因为图省位置将其塞进上游平台。

先确定主阅读方向与层级，建立列宽、对齐线、行距和边界内边距，再放置节点。相同层级的系统板块统一外框宽度与对齐基线；同类或成对模块保持一致宽度和相应高度。内容较多时先扩高、换行或分图，不通过删内容、压扁 SVG 或缩小个别字号强行等高。

“新增 / 改造 / 既有”及持久化所属边界依实际来源保留。职责卡不自动成为新部署单元，业务处理步骤也不自动成为新服务。

## 4. 量化布线：最小弯折 → 最短路径 → 最少交叉

在不穿节点、标题、文字和端口标记的前提下，优先直连；需要避障时选择短路径和最少必要转折。请求与其返回优先使用相邻平行通道，不让两者共线、重叠或共用箭头端点。给箭头与标签预留独立空间，不能让返回线穿过请求文字。三个几何指标（`B`/`L`/`C`）的定义与「最小弯折 → 最短路径 → 最少交叉」字典序由 `line_spec_path` 统一裁决，本规范不另立顺序。

先调整模块位置与端口，按 `line_spec_path` 的字典序降低弯折数、路径长度与交叉数，再布线。不要为体现线条样式制造 U 形长绕路，也不为单纯减少交叉增加弯折或长度。多条协议、替代分支或独立业务链不能因合并线路而变成串行步骤或同一个接口。

交互规范不重选线条样式：`orthogonal` 的必要转角仍为直角，`rounded-orthogonal` 的转角用真实圆角，`curved` 的主体仍保持平滑曲线。下面的局部跨线桥与全图转角样式是两回事；桥覆盖的交点仍计入 `C`，但不会因为做了桥就从布线比较中被豁免。

## 5. 相交但不连接，使用真实圆弧跨线桥

按 `line_spec_path` 的字典序（最小弯折 → 最短路径 → 最少交叉）比较后仍存在的无关线路交叉，**一律**在其中一条线上绘制真实 `A`／`Q` 圆弧桥，并在图例说明“跨线不连接”。不可只用 `stroke-linejoin=round`，也不可用连接圆点暗示相交处有业务汇流；不得以「已加桥」跳过弯折数与路径长度的比较。

正交线的桥半径参考 12 个 viewBox 单位；按相邻交点、端口和折点距离收缩，桥之间不能重叠。交点过近而无法容纳桥时应重新排布。曲线只在必要交点附近局部过桥，保持与原路径连续，不把全图改成另一种线条。

可在桥弧附近使用窄白色衬线，使下穿线路可辨；这只用于交叉消歧，不能用大块遮罩掩盖线穿文字或不合理布局。真正的 T 形汇流、共享总线连接必须连续，不能加桥切断真实连接。

验收覆盖所有实际交点，包括靠近端口和拐角的交点；不能因为交点距离短而直接忽略。桥本身也不能碰到文字、其他桥或节点。

## 6. 编号覆盖完整逻辑交互

架构交互、时序消息及流程步骤按逻辑／因果顺序编号，覆盖发起、受理、处理、结果返回或独立回调、处理确认和后续业务。请求与返回各自标注编号和角色，可用独立顺序号、`-Q/-R` 或确认阶段编号。

替代分支用 `A/B` 或清楚的子编号，旁注二选一条件，不能把替代分支编号成必然串行。独立扫描、超时、补偿等旁路可用 `T1/T2` 等编号，但不能接成主链成功后必经的下一步。

异步系统中，序号表达逻辑或因果关系，不保证全局回包先后；需要时在图例说明实际到达可以乱序。编号必须对应模型中的事件与方向，不仅是装饰在卡片上的序数。

## 7. 图种适用范围

| 图种 | 本规范如何应用 |
| --- | --- |
| 架构图 | 独立系统边界、网格对齐、调用与返回分离、交互编号和跨线桥 |
| 时序图 | 每条消息单向；返回虚线；普通消息仍水平，按时间／片段布局，不为本规范改成斜线 |
| 流程图 | 流转与条件分支单向；仅在业务确有请求／返回语义时拆返回线，不给每个处理框自动增加确认 |
| 状态图 | 迁移方向、事件／条件／动作保留；不凭空增加“返回状态”或反向迁移，编号仅在需要追踪迁移时使用 |
| ER 图 | 有向引用保持一个方向；两端鸟爪／可选性标记是基数而非双向消息箭头，不得机械删除，也不将关系编号强排成执行顺序 |

## 8. 模型、元数据与交付验收

在现有 `.diagram.json` 中增加独立对象：

```json
{
  "interaction_standard": {"id": "single-direction", "version": "1.0.0"},
  "model": {
    "connections": [
      {"id": "request-02", "from": "service", "to": "platform", "role": "request", "step": "02", "line": "solid"},
      {"id": "accepted-02-R", "from": "platform", "to": "service", "role": "acknowledgement", "step": "02-R", "line": "dashed"},
      {"id": "callback-05b", "from": "platform", "to": "result-handler", "role": "independent_request", "step": "05b", "line": "solid"}
    ]
  }
}
```

保留既有 `line_style`、视觉编号、完整 profile、模型及 `dependencies`，补入本规范和示例的实际 SHA256。几何覆盖写入 `overrides.connectors`，如 `single_direction: true`、`return_lines: separate-dashed`、桥半径和实际绕行；不要借此篡改业务状态或约束。

验收：有向交互线只有终点方向箭头；返回有独立端口、虚线、方向和编号；回调不被误当同步响应；外部系统未错误嵌套；模块对齐；短路径不穿字穿框；逐边 `B / L / C` 比较与非直连取舍依据已记录；所有必要交点有可辨圆弧且真实汇流未断开，消除交叉后无残留桥弧；模型中的步骤与分支均能在图中定位。自动检查后仍核看整图与密集交叉区域。
